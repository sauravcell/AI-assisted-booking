Wiring the Booking Agent

A walkthrough of src/telegram/telegram.service.ts, src/ai/, and src/agent/ — written for the person about to build checkAvailability, createBooking, and cancelBooking next.

1. The big picture 2. Telegram layer 3. AI layer 4. Agent layer 5. Adding your next tool Glossary

01The big picture, before the details

Three folders, three jobs. telegram/ only knows how to talk to Telegram. ai/ only knows how to turn a chat message into a saved conversation. agent/ only knows how to think and act — it has never heard of Telegram and never will. Each layer calls the one below it and hands back a plain result; none of them reach two layers down.

sequenceDiagram
    participant U as Telegram user
    participant TC as TelegramController
    participant TS as TelegramService
    participant CS as CustomerService
    participant AI as AIChatService
    participant DB as Postgres (conversations/messages)
    participant AS as AgentService (agent/)

    U->>TC: sends text message
    TC-->>U: 200 OK (ack immediately)
    TC->>TS: handleUpdate(update)
    TS->>CS: findOrCreate(telegramChatId)
    CS-->>TS: customer
    TS->>AI: chat({customerId, text})
    AI->>DB: findOrCreate conversation
    AI->>DB: save incoming user message
    AI->>DB: load full message history
    AI->>AS: invoke(state with messages)
    AS-->>AI: { response, newMessages }
    AI->>DB: save newMessages (assistant/tool)
    AI-->>TS: { response }
    TS->>U: sendMessage(reply text)

Notice the acknowledgement happens before any real work: Telegram expects a fast response to a webhook (a URL that Telegram itself calls the moment a message arrives, as opposed to your server having to repeatedly ask "any new messages?"). If you reply slowly, Telegram assumes delivery failed and retries, which would run the whole pipeline twice. That's why telegram.controller.ts sends 200 first and only then processes the update.

02The Telegram layer

Job: translate between "Telegram's JSON format" and "our internal chat request." Nothing about doctors, bookings, or LLMs lives here.

src/telegram/telegram.service.ts translator

TelegramService receives two dependencies through its constructor (constructor injection — instead of creating its own CustomerService/AIChatService internally, it accepts already-built ones from the outside. This means the class doesn't need to know how those services are built, and you can hand it fake/mock versions in tests).

async handleUpdate(update: TelegramUpdate): Promise<void> {
  const message = update.message;
  if (!message) return;
  if (!message.text) { /* text-only for now */ await this.sendMessage(...); return; }

  try {
    await this.handleTextMessage(message);
  } catch (error) {
    console.error("Telegram update failed:", error);
    await this.sendMessage(message.chat.id, "Sorry, something went wrong. Please try again.");
  }
}

Three things worth internalizing here:

  1. Guard clauses first. No message, or a non-text message (photo, sticker, voice note) — bail out early with a friendly reply instead of letting it fall through into logic that assumes text exists.
  2. One try/catch wraps the entire business flow. If anything downstream throws — the database, the LLM call, a missing tool — the user still gets a plain-English apology instead of the request silently vanishing.
  3. handleTextMessage is the real body: find-or-create the customer, call the AI layer, send the reply. That's it — three calls, no branching on what the AI actually said.
Junior-dev note: message.chat.id is typed as any right now (see telegram.types.ts), with a comment admitting the DB column is a number. If you touch customer lookup later, know that this typing is intentionally loose today, not an oversight to silently "fix" without checking the DB column type first.

03The AI layer — one file, one job: orchestration

src/ai/ai-chat.service.ts is the seam between "conversations stored as rows in Postgres" and "conversations understood as message objects by LangChain" (the library the agent is built with). It never touches the LLM directly — it only prepares input for AgentService and files away what comes back.

src/ai/ai-chat.service.ts orchestrator

AIChatService.chat() runs these steps, strictly in order:

#StepWhy it matters
1conversationService.findOrCreate(customerId) Reuses the customer's already-open conversation (a conversation here just means "a row that groups messages together," similar to one chat thread) instead of starting a new thread every message.
2messageService.saveMessage({role:"user", ...}) The incoming message is saved before history is reloaded, specifically so step 3 already includes it — no separate "append to memory" step needed.
3messageService.getConversationMessages(conversationId) Pulls the entire conversation back out of Postgres as plain {role, content} rows.
4toLangChainMessages(history) Converts those plain rows into LangChain's typed message classes (HumanMessage, AIMessage, ToolMessage) — the shape the agent layer actually speaks.
5agentService.invoke(state) Hands everything to the agent/ folder. This is the only line in the whole codebase where the "outside world" calls into the agent.
6toDatabaseMessages(conversationId, result.newMessages) + saveMany Only the messages produced during this run get saved back — not the whole history again. That's the whole reason newMessages exists as a separate field from messages (more on that in the state section below).
7conversationService.touch(conversationId) Updates last_message_at so an "active" conversation lookup in step 1 stays accurate over time.
Why this file exists at all: without it, TelegramService would need to know about Postgres rows, LangChain message types, and the graph — three concerns tangled into one class. Instead, Telegram only ever calls aiChatService.chat({customerId, text}) and gets back {response}. If you later add a web chat widget or a WhatsApp integration, they'd call this exact same method.

04The agent layer — where the thinking happens

This is a LangGraph agent (a library for building an LLM app as an explicit state machine: boxes that do work, called nodes, connected by arrows that decide what runs next, called edges — instead of one long hand-written if/else chain). Ten files, three jobs between them.

4.1 — The graph itself: how one turn actually loops

Before reading any single file, look at the shape they all plug into. This is booking.graph.ts, drawn out:

flowchart TD
    START((START)) --> LLM["llm node
(calls Groq)"]
    LLM -- "response has tool_calls?" --> ROUTE{router.route}
    ROUTE -- "yes → 'tool'" --> TOOL["tool node
(runs registered tool)"]
    ROUTE -- "no → '__end__'" --> END((END))
    TOOL --> LLM

Read that loop out loud: the LLM speaks → the router checks if it asked to run a tool → if yes, the tool runs and we go back to the LLM so it can react to the result → if no, we're done. A single user message can bounce through llm → tool → llm → tool → llm → END as many times as the model needs before it has a real answer.

src/agent/graph/booking.graph.ts graph definition 
return new StateGraph(BookingState)
  .addNode("llm", this.llm.execute.bind(this.llm))
  .addNode("tool", this.tool.execute.bind(this.tool))
  .addEdge(START, "llm")
  .addConditionalEdges("llm", this.router.route.bind(this.router), {
    tool: "tool",
    __end__: END,
  })
  .addEdge("tool", "llm")
  .compile();

The in-file comment warns not to build this across separate statements on a mutable variable — LangGraph's TypeScript types get more specific with every .addNode()/.addEdge() call, so the whole thing has to be one chained expression or the compiler loses track of what state shape each node expects.

4.2 — The shared memory: state

src/agent/state/booking.state.ts state schema

Annotation.Root({...}) defines the object that flows through every node. Each node only returns the fields it changed; LangGraph merges that partial return into the running state using a reducer (a merge function: given the old value and the node's new value, decide what the state becomes next). Every reducer here is (_, right) => right, meaning "the newest value always wins" — simplest possible reducer, no accumulation logic.

fieldwhat it's for
messagesThe full running conversation this graph invocation sees — loaded once at the start, then rewritten by llm/tool nodes as they append to it.
newMessagesOnly what this run produced. This is what ai-chat.service.ts persists — it never re-saves history that's already in Postgres.
toolResultsDeclared as a slot for raw tool output, but not currently populated by ToolNode — today tool results live inside messages as ToolMessages instead. Worth knowing this field is aspirational, not wired up yet.
responseThe final text that eventually gets sent back to the Telegram user.

4.3 — The brain: LLM node, router, and the prompt

src/agent/nodes/llm.node.ts LLM call

Every turn, this node prepends the SYSTEM_PROMPT (the persona and rules given to the model — "never invent doctors," "always use tools for real data," etc.) to the message history, then calls the model through the AIProvider abstraction (see 4.5).

const hasToolCalls = (response.tool_calls?.length ?? 0) > 0;
return {
  messages: [...state.messages, response],
  newMessages: [...state.newMessages, response],
  response: hasToolCalls ? state.response : response.text,
};

That last line is the subtle bit: response (the field the user eventually sees) is only overwritten when the model did not ask for a tool call. If it did, we keep whatever was there before — because this turn's "answer" is really just "please run this tool for me," not something to show the user yet.

src/agent/nodes/router.node.ts pure decision

The smallest file in the folder, and deliberately so — it makes exactly one decision and has no side effects (calls no database, no network, nothing "impure"): is the last message an AIMessage with at least one tool_calls entry? If yes → "tool". Otherwise → "__end__". This return value is literally the key LangGraph uses to pick the next node in the conditional edge map you saw in booking.graph.ts.

src/agent/prompts/system.prompt.ts persona & rules

A single SystemMessage (LangChain's wrapper for "instructions the model should treat as ground rules, not part of the conversation"). This is the one file you'd edit to change the assistant's tone, or to add a new rule like "always confirm the appointment time back to the user before calling createBooking."

4.4 — The hands: tools, the registry, and the adapter

src/agent/nodes/tool.node.ts tool executor

When the router sends us here, this node reads tool_calls off the last AI message — there can be more than one, since a single model turn can ask to run several tools at once — and for each one:

const tool = this.registry.get(toolCall.name);
if (!tool) throw new Error(`Unknown tool: ${toolCall.name}`);

const result = await tool.execute(toolCall.args);

toolMessages.push(new ToolMessage({
  tool_call_id: toolCall.id,
  content: JSON.stringify(result),
}));

tool_call_id is what lets the model later match "the result I'm reading" back to "the specific call I asked for" — important once more than one tool call happens in the same turn. Notice ToolNode never imports SearchDoctorTool or any concrete tool class directly — it only knows the ToolRegistry. That indirection is deliberate, covered next.

If you forget to register a tool, this is where it explodes at runtime with Unknown tool: yourToolName — not at compile time. Keep that in mind once you start adding createBooking.
src/agent/registry/tool.registry.ts phone book

A thin wrapper around Map<string, AgentTool> with register(), get(), has(), getAll(). The in-file comment diagrams the intent well:

ToolNode
     ↓
ToolRegistry
     ↓
SearchDoctorTool
     ↓
BookingService

This is the Dependency Inversion Principle in practice: ToolNode depends only on the abstract idea of "a tool with a name," never on a concrete class. New tool → register it in one place (agent.bootstrap.ts) → nothing in graph/ or nodes/ needs to change.

src/agent/tools/agent-tools.ts tool contract

The AgentTool interface every tool implements: name, description (sent to the model so it knows when to reach for this tool), schema (a Zod schema — Zod is a runtime validation library; here it doubles as the definition of what arguments the model is allowed to pass), and execute(input).

src/agent/tools/searchDoctor.tool.ts working example 
export class SearchDoctorTool implements AgentTool<SearchDoctorToolInput> {
  readonly name = "searchDoctor";
  readonly description = "Search doctors by doctor name or specialization.";
  readonly schema = z.object({ keyword: z.string().optional() });

  constructor(private readonly doctorService: DoctorService) {}

  execute(input: SearchDoctorToolInput) {
    return this.doctorService.searchDoctors(input);
  }
}

This is the template to copy. Notice execute() does no SQL and no business logic of its own — it just forwards to DoctorService. The rule stated in agent-tools.ts's own doc comment: "The tool should never contain SQL. It delegates to Services." A tool's only job is translating between "what the LLM is allowed to ask for" and "the service method that actually does it."

checkAvailability.tool.ts · createBooking.tool.ts · cancelBooking.tool.ts empty stubs

All three exist as empty files today. So do booking.service.ts, booking.repository.ts, and booking.types.ts in src/booking/. This is the actual next milestone — Section 5 below walks through exactly how createBooking would slot into everything you just read.

src/agent/adapters/langchain-tool.adapter.ts format converter

toLangChainTools() takes our internal AgentTool[] and wraps each one with LangChain's own tool() factory function — the exact shape ChatGroq's .bindTools() expects (function calling/tool calling: the mechanism by which an LLM API lets the model "ask" your code to run a named function with structured arguments, instead of only returning free text). Our own AgentTool interface never has to know LangChain exists — this adapter is the only file that bridges the two.

4.5 — Swappable model access: the provider abstraction

src/agent/providers/ai-provider.ts interface 
export interface AIProvider {
  invoke(messages: BaseMessage[]): Promise<AIMessage>;
}

One method. That's the entire contract LLMNode depends on.

src/agent/providers/groq.provider.ts Groq implementation

The file's own header comment says it plainly: "The rest of the application never imports ChatGroq. Only this file knows Groq exists." (Groq is the LLM hosting service this project currently calls; a Runnable is LangChain's umbrella type for "anything invokable with .invoke()" — here, a chat model that already has tools bound to it via bindTools(), built in agent.bootstrap.ts.) Swapping to OpenAI or Anthropic later means writing a new file next to this one and changing one line in the bootstrap — nothing else in agent/ changes.

4.6 — Translating between Postgres rows and LangChain messages

src/agent/utils/message.mapper.ts DB ⇄ LangChain

Two directions, both used by ai-chat.service.ts:

  • toLangChainMessages(dbRows) — turns {role: "user"|"assistant"|"tool", content} rows into HumanMessage/AIMessage/ToolMessage instances the graph can work with.
  • toDatabaseMessage(s) — the reverse, turning LangChain message instances back into plain rows to insert.

extractContent() exists because LangChain's content field isn't always a plain string — some providers can return structured content (arrays of content blocks). This helper safely coerces it to a string before it's stored in a text column.

4.7 — The front door: AgentService

src/agent/service/agent.service.ts facade 
export class AgentService {
  private readonly graph;
  constructor(bookingGraph: BookingGraph) {
    this.graph = bookingGraph.build();
  }
  invoke(state: BookingAgentState) {
    return this.graph.invoke({ ...state, newMessages: [] });
  }
}

This is a facade (a design pattern: a small class whose only job is to hide a more complicated subsystem behind a simple front door). Everything you read above — the graph, the nodes, the registry, the provider — is invisible to ai-chat.service.ts. It only ever sees agentService.invoke(state). Note it resets newMessages to [] right before invoking, guaranteeing each run starts counting its "new" output from zero, regardless of what the caller passed in.

4.8 — Where it's all assembled: the bootstrap

src/bootstrap/agent.bootstrap.ts composition root

This is the file that actually new's everything up and wires it together — sometimes called the composition root (the one place in an app where concrete objects get constructed and handed to each other, so the rest of the codebase can stay decoupled and just depend on interfaces). Read top to bottom, it is literally the assembly order:

const doctorRepository = new DoctorRepository();
const doctorService = new DoctorService(doctorRepository);

const registry = new ToolRegistry();
registry.register(new SearchDoctorTool(doctorService));

const langchainTools = toLangChainTools(registry.getAll());

const chat = new ChatGroq({ apiKey: ..., model: ..., temperature: 0 });
const provider = new GroqProvider(chat.bindTools(langchainTools));

const llmNode = new LLMNode(provider);
const routerNode = new RouterNode();
const toolNode = new ToolNode(registry);

const graph = new BookingGraph(llmNode, routerNode, toolNode);
return new AgentService(graph);

This function runs once, at import time (export const agent = createAgent(); at the bottom of the file), triggered indirectly the moment telegram.bootstrap.ts imports it — which happens because telegram.routes.ts imports telegram.bootstrap.ts, which is imported by routes/index.ts, which app.ts mounts on startup. One agent singleton, built once, reused for every message.

05Adding your next tool: a worked checklist

Using createBooking as the running example, since it's one of the three empty stubs waiting for you.

  1. Build the real logic first, with no AI involved. Fill in booking.types.ts (a Booking shape and a CreateBooking input shape), booking.repository.ts (the SQL — insert a row into whatever bookings table exists), and booking.service.ts (validation like "is this slot still free" before calling the repository). Model these three files after doctor.repository.ts/doctor.service.ts, which you already have working examples of.
  2. Write the tool class in createBooking.tool.ts, implementing AgentTool exactly like SearchDoctorTool does: pick a name the model will call (e.g. "createBooking"), write a description clear enough that the model knows when to use it, define a Zod schema for the arguments (doctor id, date, time, customer id…), and have execute() call straight into BookingService — no SQL in this file.
  3. Register it in agent.bootstrap.ts: construct BookingRepository/BookingService next to the doctor ones, then add one line: registry.register(new CreateBookingTool(bookingService));. That's the only file that needs to change to make a new tool available — the graph, nodes, and registry code never change.
  4. Update the system prompt if the model needs new rules — e.g. "always confirm date, time, and doctor name back to the user before calling createBooking," so it doesn't book something the user didn't actually confirm.
  5. Test it in isolation first, without touching Telegram or the database round-trip, using npm run test:agent (src/scripts/test-agent.ts) — edit the hardcoded prompt in that file to something like "Book me with Dr. Smith tomorrow at 10am" and watch the console logs llm.node.ts and tool.node.ts already print for every step.
Don't forget: if createBooking needs to check availability first, that's exactly what checkAvailability.tool.ts is for — you may end up building two tools and letting the model decide to call checkAvailability before createBooking on its own, across one llm → tool → llm → tool → llm loop, rather than hard-coding that sequence yourself. That's the entire point of the graph looping back to llm after every tool call.

—Glossary, for quick lookup

Webhook
A URL you give to a third-party service (here, Telegram) so it can push events to you the moment they happen, instead of you having to poll and ask "anything new?" on a timer.
Constructor injection
Passing a class's dependencies in through its constructor rather than having it create them internally, so callers control what implementation it gets (real service, test double, different provider, etc).
Node / edge (LangGraph)
A node is a function that receives the current state and returns the parts of it that changed; an edge decides which node runs next. A "conditional edge" picks the next node based on a function's return value at runtime.
Reducer (state)
The merge function LangGraph calls to combine a state field's old value with what a node just returned for it. Every reducer in this project simply replaces the old value with the new one.
Tool calling / function calling
An LLM API feature where, instead of only returning text, the model can return a structured request to run one of the functions you described to it, along with arguments matching a schema you provided.
Zod schema
A runtime validation library. Here it's dual-purpose: it validates a tool's input at runtime, and its shape is also translated into the argument definition the LLM sees for that tool.
Facade (pattern)
A class that exposes one simple method to hide a more complex subsystem behind it — AgentService.invoke() hides the entire LangGraph graph from its caller.
Dependency Inversion
Depending on an abstraction (like the AgentTool interface or the ToolRegistry) instead of a concrete class, so new implementations can be added without changing the code that uses them.
Composition root
The one place in the app (agent.bootstrap.ts / telegram.bootstrap.ts) where concrete objects are actually constructed and wired together with new, so everywhere else can just depend on interfaces.
