Technical Overview — Internal

How the AI Agent Talks to the Database

A walkthrough of how a patient's message on Telegram turns into a real, safe database read or write — and why the language model itself never touches SQL.

Scope — booking agent request path Stack — Node/TypeScript, LangGraph, Groq, PostgreSQL Audience — new to this architecture

01The big picture

In one sentence: the model never runs SQL — it asks, in structured JSON, for a capability like "search doctors" or "book this slot," and ordinary trusted application code decides how that turns into a parameterized query.

The system has two halves that hand off to each other in a loop. The reasoning half is a large language model (LLM) that reads the conversation and decides what to say or what to ask for next. The data half is plain TypeScript — services and repositories — that knows how to query Postgres. The LLM is never given a database connection; it can only request one of a fixed set of named actions, and those actions are the only door into the database.

Everything below unpacks one hop of this diagram at a time — starting with the vocabulary, since a few of these terms (agent, tool calling, LangGraph) will be new.

02Concepts you'll need

A short glossary before the walkthrough — skip anything you already know.

LLM
The language model itself (here, a Llama model served by Groq). Given a list of messages, it returns one message back — plain text, or a request to call a named function.
Tool calling
A mode where the LLM is shown a list of function names + schemas (no code, just names and typed parameters) and can respond with "call checkAvailability with doctorId: "..."" instead of text. The model never executes anything — it only asks.
Agent
The loop that keeps feeding the model's tool requests back to it with results, until it stops asking for tools and produces a final answer. "Agent" just means "LLM + a loop + a set of tools it can request."
LangGraph
The orchestration library used to implement that loop as an explicit state machine (a "graph") instead of hand-rolled while logic. Two nodes matter here: llm and tool.
Zod schema
A TypeScript validation library. Every tool declares its expected input shape as a Zod schema, which doubles as (a) the contract shown to the LLM and (b) a runtime guard against malformed or hallucinated arguments.
Repository
The one place per data type (doctors, bookings, messages…) allowed to write raw SQL. Everything above it works with plain objects, never rows or query strings.
Connection pool
A small set of reusable Postgres connections (here, pg.Pool, max 10) that repositories borrow from per query instead of opening a new connection each time.
Row lock (FOR UPDATE)
A SQL clause that locks the selected row until the transaction commits, so two simultaneous requests can't both grab the same appointment slot.

03A request, step by step

Concretely, here's what happens when a patient books an appointment.

  1. Message arrives

    Telegram posts the update to a webhook. TelegramController replies 200 immediately (Telegram retries otherwise) and hands the message to TelegramService to process asynchronously.

  2. Identity resolves to a customer row

    CustomerService.findOrCreate looks the Telegram chat ID up in the customers table, creating a row on first contact. From here on, the conversation is tied to a real customerId — not a Telegram ID.

  3. The message is persisted before the AI ever sees it

    AIChatService finds or opens a conversations row, then saves the incoming text into the messages table straight away. If anything downstream fails, the user's message is never lost.

  4. Full history is reloaded from Postgres

    Every message ever exchanged in this conversation is read back out and converted into LangChain message objects. The agent has no memory of its own between requests — more on this below.

  5. The graph runs: LLM ⇄ tool, until done

    The system prompt plus the full history go to Groq. If the reply contains tool calls, ToolNode executes them and feeds JSON results back in; the graph loops back to the LLM. Once a reply has no tool calls, RouterNode ends the loop.

  6. Every tool call becomes a real, parameterized query

    Searching doctors, checking slots, creating or cancelling a booking — each is a repository method running SQL against Postgres, detailed in the next section.

  7. The turn is written back and returned

    All the new messages generated this turn (tool calls, tool results, the final answer) are saved to messages, the conversation's last_message_at is touched, and the final text is sent back through Telegram.

04How the AI actually touches the database

This is the part that matters most: the model requests, trusted code decides.

The LLM is bound to four tools — searchDoctor, checkAvailability, createBooking, cancelBooking — each described to it only by name, a plain-English description, and a Zod schema. That's the entire surface the model can see. It cannot see SQL, table names, or connection details, because none of those are part of a tool's public shape.

src/agent/tools/agent-tools.ts
// Every tool the LLM can call implements this shape.
interface AgentTool<TInput, TOutput> {
  readonly name: string;             // e.g. "checkAvailability"
  readonly description: string;      // shown to the LLM
  readonly schema: ZodType<TInput>;    // shown to the LLM + validated at runtime
  execute(input: TInput, context: ToolContext): Promise<TOutput>;
}

When the model asks to call one, ToolNode does not trust the arguments blindly. It re-validates them against that same Zod schema before anything touches a repository:

src/agent/nodes/tool.node.ts
// A malformed or hallucinated argument becomes a normal tool
// result the LLM can react to — never a crash mid-conversation.
const parsedArgs = tool.schema.safeParse(toolCall.args);

const result = parsedArgs.success
  ? await tool.execute(parsedArgs.data, { customerId: state.customerId })
  : { success: false, reason: "INVALID_INPUT", message: "..." };
Note the customerId in that snippet comes from state — the graph's own trusted state — not from toolCall.args. The model is never asked for, and could never supply, whose booking to create or cancel. That identity is injected by the app, closing off an entire class of "make the AI act as someone else" bugs.

From there it's an ordinary call stack: Tool → Service → Repository → pg.Pool.query(). No layer above the repository ever sees a table name or writes a query string.

05Layered architecture

The agent is deliberately kept ignorant of the database; only the bottom layer knows SQL exists.

searchDoctor calls Doctor Service; the other three tools call Booking Service — both ultimately hit the same Postgres instance through their own repository.

Two things fall out of drawing it this way. First, the ToolNode never imports a concrete tool class directly — it asks the ToolRegistry for whatever tool matches the name the model produced. New capabilities are added by registering a new tool, not by editing the graph. Second, services contain no SQL — BookingService and DoctorService read as plain business logic; only BookingRepository and DoctorRepository ever import pg or write a query string. If Postgres were swapped for something else, this is the only layer that would need to change.

06Safety & correctness guarantees

Booking a slot is a transaction, not two separate writes

Two patients can message the bot for the same slot within the same second. bookSlot opens a transaction, locks the availability row with FOR UPDATE, re-checks is_available, and only then inserts the booking and flips the slot — all inside one commit. The second request to reach that row simply sees it's already taken.

src/booking/booking.repository.ts
await client.query("BEGIN");
const { rows } = await client.query(
  `SELECT * FROM doctor_availability WHERE id = $1 FOR UPDATE;`, [availabilityId]
);
// ...re-check is_available, then INSERT/UPDATE the booking...
await client.query(
  `UPDATE doctor_availability SET is_available = false WHERE id = $1;`, [availabilityId]
);
await client.query("COMMIT");

Expected failures are data, not exceptions

"Slot already taken," "booking not found," "this booking isn't yours" are all ordinary return values ({ success: false, reason: "..." }), not thrown errors. They flow back to the LLM as a tool result so it can explain the outcome in plain language, instead of the whole turn failing. The system prompt reinforces this explicitly: tool results are the model's only source of truth — it's instructed never to invent a doctor, slot, or booking ID.

Every SQL value is parameterized

Every query in every repository uses $1, $2, … placeholders with a separate values array — never string-concatenated input — so nothing the model (or the patient) types can alter query structure.

07Where "memory" actually lives

It's tempting to think of the agent as a long-running process that remembers a conversation. It doesn't — the agent itself is stateless. Each incoming message triggers a fresh invocation with no memory of the previous call in the process. What looks like memory is the messages table: the entire history is re-read from Postgres and replayed to the LLM on every single turn.

This has a practical consequence worth knowing: conversation length is bounded by how much history the model can be sent, not by any session or cache — and history really is the full row set for that conversation_id, ordered by created_at.

09Adding a new capability

Because of the layering above, adding something like "reschedule an appointment" is additive, not invasive:

  1. Add the data method

    A new method on BookingRepository (SQL) and BookingService (business rule) if one doesn't already fit.

  2. Write the tool

    A class implementing AgentTool — name, description, Zod schema, and an execute that calls the service. No graph code changes.

  3. Register it

    One line in agent.bootstrap.ts: registry.register(new RescheduleBookingTool(bookingService)).

  4. Tell the model when to use it

    A line in tool-rules.prompt.ts so the system prompt's rules stay in sync with what's actually registered.
